MPI Laplacian Assembly

lap_dg_2d_mpi_main.cpp and lap_dg_3d_mpi_main.cpp are the MPI-parallel counterparts of the standard (sequential) Laplacian DG assembly examples one level up in examples/assembly/laplacian/. Configuration parsing (JSON + CLI) is shared with those sequential examples via lap_common.hpp; lap_mpi_common.hpp in this directory only adds what is genuinely MPI-specific: aborting the whole job on error, and the dimension-specific mesh-kind option lists.

Single-run, not a convergence study

Unlike the sequential examples, these are single-run examples: each invocation solves the Laplacian problem on exactly one mesh and exports one solution. There is no n_lvls / refinement-level loop and no convergence table.

This is intentional, not a missing feature:

  • The coarsest mesh in a convergence hierarchy caps how many MPI ranks can usefully be used (you can't partition a handful of cells across dozens of ranks).
  • Building a full agglomerated mesh hierarchy (k-means/GNN/ParMETIS) is expensive; doing it repeatedly as part of routine MPI testing isn't practical.

If you need a convergence study, run the sequential examples (any number of MPI ranks works there too, since they don't parallelize the mesh) and compare against a single MPI run at matching parameters as a sanity check.

Running

Configuration parsing is shared with the sequential Laplacian examples (examples/assembly/laplacian/lap_common.hpp): there is no automatic search for a default JSON file and no silent fallback to compiled-in defaults. Exactly two invocation modes are valid:

1. JSON, optionally with positional overrides:

mpirun -n <P> ./lap_dg_2d_mpi_main JSON [order] [mesh_kind] [nel] [dof_distrib_type] [mesh_file] [output_path]

The JSON path is loaded explicitly; the program fails with a clear error if it cannot be opened or parsed. Any positional arguments after it override the corresponding JSON values, in the order shown above.

2. Positional only, no JSON:

mpirun -n <P> ./lap_dg_2d_mpi_main order mesh_kind nel dof_distrib_type [mesh_file] [output_path]

order, mesh_kind, nel, and dof_distrib_type are mandatory in this mode; missing any of them is a hard failure with a usage message, not a silent default. mesh_file and output_path are genuinely optional (defaults: empty / output/laplacian).

The same two modes apply to lap_dg_3d_mpi_main. -h/--help prints full usage and the mesh-kind list.

Examples

JSON only:

OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 \
mpirun -n 4 ./lap_dg_2d_mpi_main \
../examples/assembly/laplacian/MPI/lap_2d_mpi_parameters.json

JSON with a positional override (order bumped to 3):

OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 \
mpirun -n 4 ./lap_dg_2d_mpi_main \
../examples/assembly/laplacian/MPI/lap_2d_mpi_parameters.json 3

Positional only, no JSON file:

OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 \
mpirun -n 4 ./lap_dg_2d_mpi_main 2 tria 8 2

Fields

Field Meaning
order Polynomial order (>= 1)
mesh_kind Mesh type, see below
nel Mesh size/selector; meaning depends on mesh_kind
dof_distrib_type 0 = default DoF numbering, 2 = MPI subdomain-wise (default)
mesh_file Path to a mesh file, only used when mesh_kind = "load_file"
output_path Directory the .pvtu/.vtu output is written to

dof_distrib_type = 2 is the recommended/default setting: local submesh projection (used for export) requires owned-cell DOF coefficients to be locally owned, which subdomain-wise renumbering guarantees.

Supported <tt>mesh_kind</tt> values

2D:

  • tria, sqr — structured Cartesian mesh, nel x nel cells
  • poly_meshes — a single polygonal mesh, nel selects test/data/mesh/Mesh_P_<nel>.vtk (one of 8, 16, 20, 32, 64, 128, 256, 512, 1024, 2048)
  • kway_kmeans — k-means direct k-way agglomeration, target nel*nel groups
  • bisect_kmeans, bisect_gnn — k-means/GNN bisection agglomeration, nel bisection levels
  • load_file — read mesh_file directly (.vtk or .vtu)

3D:

  • tet, hexa (alias cart) — structured Cartesian mesh, nel x nel x nel cells
  • poly — a pre-tetrahedralized mesh, nel selects test/data/mesh/mesh_tet_<nel>p.vtu (one of 48, 384, 1296, 3072)
  • load_file — read mesh_file directly (a full 3D .vtu mesh)

**load_file behavior:** mesh_file must be set and non-empty, or the example fails immediately with a clear error. If mesh_file is set, nel is ignored (a warning is printed); it is never used as a file index.

Not supported yet (either mesh_kind): kway_metis, bisect_metis (ParMETIS agglomeration, 2D only), and periodic mesh kinds. Requesting one prints a clear message and aborts the MPI job — see Limitations below.

Threads per MPI rank

Each -n <P> MPI rank is its own process, and each of those processes may itself use several threads for VTK/OpenMP work and for BLAS operations inside PETSc. Rank count and thread count are configured independently:

  • OMP_NUM_THREADS selects the VTK/OpenMP thread budget.
  • If OMP_NUM_THREADS is missing or invalid, VTK falls back to one thread and Vulpes prints a warning.
  • OPENBLAS_NUM_THREADS directly controls OpenBLAS, and may intentionally differ from OMP_NUM_THREADS (e.g. more VTK threads than BLAS threads per rank).
  • If OPENBLAS_NUM_THREADS is not set, OpenBLAS is expected to follow OMP_NUM_THREADS instead.
  • Vulpes checks the active OpenBLAS thread count after PETSc initialization but never changes it — mismatches are only reported.
  • OpenBLAS may spawn its threads before main() runs, so both variables must be set in the environment before launching the program. PETSc's -blas_num_threads option can steer later BLAS calls, but it may be too late to prevent that pre-main() thread creation.

See the OMP_NUM_THREADS/OPENBLAS_NUM_THREADS prefixes in the Running examples above — the two variables can be set independently, e.g. OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=1 for more VTK/OpenMP threads than BLAS threads per rank.

For a persistent default (e.g. one thread per rank), the devcontainer Dockerfile and the Apptainer definition in the installation guide both set OMP_NUM_THREADS/OPENBLAS_NUM_THREADS as image-level defaults. Rebuild the image (or the .sif) after changing them; either variable can still be overridden per-run as shown above.

What gets exported

ParallelMesh distributes the mesh; assembly, solve (CG + BlockJacobi), and the residual/mass-projection solve for the exact solution all run in parallel via PETSc. Only PETSc-global, MPI-safe error norms are reported: errL2 and errH1 (matrix-based, via assemble::dg::computeError).

The solution is exported with MeshExporterSubmesh + projectSolutionSubmesh() to a single .pvtu (with the per-rank .vtu pieces alongside it) under output_path, with three fields:

  • u_h — the computed solution
  • u_exact — the projected exact solution
  • u_error — u_h - u_exact

Known limitations / TODOs

  • ParMETIS agglomerated mesh support (kway_metis/bisect_metis, 2D). Not implemented: see the next item.
  • Distributed agglomerated mesh pipeline. ParmetisAgglomeration itself calls ParMETIS collectively across all ranks, but ParallelMesh's mesh-generator lambda only runs on rank 0 — the two don't compose today without first agglomerating collectively and then redistributing the rank-0 result again. The right fix is to keep an agglomerated mesh distributed directly instead of round-tripping through a rank-0 full mesh.
  • MPI-reduced volume integral errors. errL2int/errH1int (as computed by the sequential examples) sum only over each rank's owned cells with no MPI reduction; adding them here would silently report a wrong per-rank-partial error until a global sum reduction is added.
  • MPI-correct DG/jump face errors. Similarly, errJump/errDG need careful handling of partition-interface faces so they're counted exactly once, not per-rank.
  • Periodic mesh support. Not implemented for MPI.
